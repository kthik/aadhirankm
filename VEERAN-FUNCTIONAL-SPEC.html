01System overview

Veeran runs a Silambam competition end to end: registration, event entry, bout assignment, judging, results, medals and reporting.

The platform is a React single-page app talking to an Express API. There is no database server: each table is a JSON file on disk, written through a temp file and an atomic rename so an interrupted write cannot leave a half-written document. That makes the system portable enough to run on a laptop at a venue with no infrastructure, and is the reason the database can live in a synced Google Drive folder (§11).

Design decisions that shape every feature

  • Nothing derivable is stored. A competitor's age band, whether they are scored, their running order and a bout's completion state are all computed on read from the entries and the filed score sheets. No status field can go stale, and editing an age range re-categorises everyone immediately.
  • Features are switchable. Thirteen modules can be turned off in one config file, and each is enforced on both sides — the API 404s the routes, the interface drops the tabs (§3).
  • Every record belongs to a tournament. One tag carries scoping, filtered reporting and filtered backup (§6).
  • Destructive actions are separate, explicit and logged. Backup never deletes; deleting reports what it will remove and demands confirmation; moving the database demands the operator's own password (§11, §12).
Scale

The JSON layer suits a single API process. It is not safe for several server processes writing the same folder at once — including two machines pointed at one Drive folder, where Drive resolves a collision as a conflict copy rather than a merge.

02Roles and access

Six roles. Each sign-in is a UID plus password; the session is a signed HTTP-only cookie valid for eight hours.

RoleUIDHomeCan do
Super Admin SA001 /super-admin Everything. Owns events, tournaments, admin accounts, the database location, restore and filtered deletes. Overrides tournament restrictions.
Admin AD00n /admin Runs the competition: academies, competitors, bouts, judges, bout assignment, analytics, full backup. May be restricted to named tournaments.
Judge J00n /judge Sees only their own bouts; scores the competitors in them.
Academy A00n /academy Registers its own competitors (single or bulk), sees its squad's progress and podium, resets its own password.
Academy participant P00n /participant Sees their own entries, results and score breakdown; edits their profile.
Individual P00n /participant As above, for a competitor entering without an academy.

Identity rules

  • UIDs are sequential per entity with a configured prefix — A001, P001, J001, E001, B001, T001. They are derived by scanning existing rows, not from a counter, so restoring a snapshot cannot desynchronise the sequence.
  • New accounts get the configured default password (pass@123). Anyone still on it sees a prompt to change it.
  • Passwords are stored as scrypt hashes. A reset returns the new password once, for the admin to read out; an existing password can never be read back.
  • Deactivating a judge or academy blocks sign-in without deleting their records.
Deployment

Set VEERAN_SECRET in the environment before deploying. Without it session cookies are signed with a fixed development key.

Relationship

A competitor entered in several events sits in one bout per event, so the competitor-to-bout link is a row in BoutEntries rather than a field on the competitor. Scores live in their own collection keyed by judge and competitor, so one judge's sheet can never collide with another's and registration data is never touched by scoring.

05Identity and registration

Four ways a competitor enters the system. All of them issue a UID and the default password, shown once on a confirmation card.

Individual sign-upCompetitor, no account neededChosen on the form Creates the competitor with no academy and an INDIVIDUAL login.

The tournament picker

Both public forms open with Registering for, listing tournaments that are active, dated and not finished — the current and upcoming competitions, never a closed one. Each option says whether it is on now or when it starts, and selecting one reveals its dates, location and venue address so two competitions cannot be confused.

  • An unchosen, unknown, ended or deactivated tournament is a field error, not a silent fallback — filing an entry under the wrong competition is worse than asking again.
  • With the tournaments module off, or nothing open, the field disappears and entries are filed under the current tournament.
  • A blank end date means open-ended: such a tournament keeps taking entries until it is switched off.

Bulk upload rules

  • The template carries an Event Codes reference sheet; the Events column accepts codes, full event names, or a comma/semicolon list of either.
  • Blank Mobile, Address or Location inherit the academy's.
  • Import is all-or-nothing: if any row fails, nothing is saved and every bad row comes back with its spreadsheet row number and per-field errors.
  • Duplicates within the academy (same name and mobile) are rejected.
  • The spreadsheet is parsed in the browser and posted as JSON, so the API needs no upload handling.

Forgot UID

Recovery requires academy name, coach name and phone to all match. A partial match returns the same "contact an Admin" answer as no match, so the endpoint cannot be used to enumerate academies.

06Tournaments

A tournament is the unit of scoping, reporting and filtered backup. Academies, competitors, judges, bouts, entries, scores and medals all carry its id.

  • Fields. Name, description, location, venue address, start date, end date, status. The venue address is what a competitor sees when they pick it on the registration form.
  • Auto-close. A tournament switches itself off once its end date passes. The sweep runs on boot, on a timer, and on demand. End dates are inclusive — one ending today is still running.
  • Reactivation. Switching a finished tournament back on is refused rather than quietly undone by the next sweep; extend the end date instead.
  • Admin scope. An admin can be narrowed to named tournaments; their dashboards, lists and analytics then show only those. An admin with none listed is unrestricted. Super Admin always overrides the restriction.
  • Migration safety. On first boot a tournament is seeded and every untagged row is tagged with it, so enabling this over a running competition orphans nothing.

07Bouts and running order

A bout is a judged group. Nothing about order or state is stored — it is derived from the entries plus the filed sheets on every read.

Assignment

  • A bout belongs to exactly one judge. Assigning a bout that is already held is refused until the admin confirms; confirming clears the previous judge's link first, so a bout is never held twice.
  • A bout may be scoped to an event and an age category. Its eligible list is then the competitors matching both who are not already in another bout for that event.
  • A competitor may hold at most one bout per event — two would mean being judged twice for it.
  • A judge may hold several bouts and gets one tab per bout.

Derived state

StateMeaningJudge sees
scoredThis judge has filed a sheet for themRow with result, sorted to the bottom
readyThis is their active boutClickable row
blockedThey are due in another bout firstIn other performance, greyed out

Active bout. Of a competitor's unscored entries, the one with the lowest queue number runs first, the lower bout id breaking a tie. Both are fixed at assignment, so a row cannot flip state because somebody else was scored.

Order within a bout. Competitors entered in more events come first, so they have time to prepare for their next event; then queue number; scored rows drop to the bottom.

Enforced

The block is not only visual. POST /api/scores refuses a sheet for a competitor whose active bout is elsewhere, so a stale page cannot score around it.

08Scoring

One sheet per judge per competitor per bout. Submitting doubles as revising.

  • Categories load from ScoreCategory — at most five active — and each accepts 0 to 10. The total is the sum.
  • A position is chosen from PositionMaster: 1 to 4, or Disqualified or Absent.
  • Re-opening a scored competitor pre-fills their sheet, so a correction is the same action as the original entry.
  • A competitor counts as complete once any judge has filed a sheet for them.
  • Scoring never writes to the competitor's registration row.

09Champions and medals

Podium places grouped by bout, with gold, silver and bronze totals.

  • Each winner carries an issued checkbox. Ticking it asks for confirmation, then records who handed the medal over and when, and locks the box.
  • Issuing is deliberately one-way: handing over a medal is a physical act, not a toggle.
  • The handover lives in its own Medals record, so a judge revising a sheet cannot undo it.

10Analytics

Every dashboard opens on figures rather than a form. All of them are computed per request from competitors and their filed sheets, so no figure can disagree with the table it came from.

  • Filters: tournament, event, age category, academy, registered-between dates
  • Headline totals, then progress split by event, age band and academy
  • Cumulative registered-versus-scored trend
  • A card per tournament with the same measures for that tournament alone

Admin

Overview, List view, Categories, Champions

  • Participants, events, bouts, judges active, completion %, average score
  • Event cards, the bout completion grid, per-judge throughput
  • Filtered list with CSV export that matches the screen exactly

Academy

Its own squad only

  • Squad size, entries, how many are in a bout, scored %, medals, average
  • Entries per event with a scored / waiting split
  • The academy's podium

Judge and competitor

Personal scope

  • Judge: assigned, completed and blocked across their bouts, then per bout
  • Competitor: events entered, judged, medals, best position, age group, and a per-category breakdown for each judged event

Drill-downs. Clicking an academy, competitor, judge or age category opens their full record — squad and sign-in state, event history and every judge's sheet, a judge's bouts and filed sheets, or everyone in an age band. Competitors and judges are editable from the drawer.

One row per event. In the filtered list, a competitor entered in several events gets one row per event, all sharing their registration ID, each showing that event's own bout and result. Filtering by event narrows to that event's rows.

11Database location

One switch decides where the JSON collections live. Super Admin can change it from the Database tab; the running server repoints without a restart.

DriverThe database isLocal folder is
local storage.local.dataDir on this machine (default server/data) the database itself
gdrive storage.gdrive.dataDir inside the synced Google Drive folder, so several machines share one database a read-through cache of it

Drive plus local cache

  • Reads are served from the local copy; the Drive file's timestamp is checked first and a newer Drive copy is pulled down, which is how another machine's change is picked up.
  • Writes go to Drive first, then mirror into the cache. A failed Drive write fails the request — an accepted write living only in the cache would vanish on the next refresh. A failed cache write only warns, because a stale cache self-corrects.
  • Drive offline leaves reads working from the cache and refuses writes, so the app degrades to read-only instead of going down.
  • Sign-in to Drive is handled by Google Drive for desktop at the operating-system level; the app holds no Google credentials. The account field on the Database tab is a label for operators, not a login.

Changing location safely

  1. Check location resolves the destination and reports what is already in it. Nothing is written.
  2. Save location opens a dialog naming the source, the destination and its contents, and asks whether to copy the current data across.
  3. The change applies only after the acting Super Admin re-enters their own password.
Copy decisionDestination stateOutcome
CopyemptyAll collections written across, then the switch
Copyalready holds dataBlocked until the "will be replaced" box is ticked
Don't copyhas a Super Admin loginAllowed, with an alert that the old data stays behind and is no longer read
Don't copyno Super Admin loginRefused
The guard

After a switch, the destination must contain an active Super Admin login — either copied across or already there. Otherwise nobody could sign in to administer the new location and the real database would be stranded at the old path. The refusal is enforced in the dialog and again on the server, and nothing is ever deleted from the old folder.

Environment overrides

VariableEffect
VEERAN_DB_DRIVERRun on the other driver for one session

An override wins over the config file; the Database tab says so when one is set. Paths accept absolute or project-relative forms, ~, and %VAR% / $VAR. The resolved folder is logged on boot and a missing Drive folder is fatal at startup rather than silently writing a second copy of the database.

12Backup, restore and delete

Export is one Excel workbook, a sheet per table. Lists and score maps are written as JSON text in their cell so a round trip is lossless.

ActionWhoBehaviour
Full backupAdmin Super AdminEvery table, no filter
Filtered backupSuper AdminBy tournament, academy, competitor or date range
Delete a selectionSuper AdminSeparate call, reports what it would remove, refuses without an explicit confirm
RestoreSuper AdminPreview first, then merge; duplicates skipped
  • Backup and delete are separate actions. A download that also wipes data on the way out is far too easy to fire by accident.
  • They read a filter differently, on purpose. A backup of one competitor carries their academy, bout and judge so the file makes sense alone; deleting that competitor must not take their academy and judge with them. An academy is owned by an academy or tournament filter; judges and bouts only by a tournament filter.
  • Restore never overwrites. A row whose key already exists is left alone, so a restore is safe to run twice and cannot replace work done since the backup. deleteBefore clears matching records first for a true replace.
  • A failure part-way through a restore rolls every table back.
  • Only genuinely numeric fields (age, total, queueNo, order, minAge, maxAge) parse back as numbers, which keeps a mobile number from becoming an integer.

13Audit log

An append-only record of administrative actions, readable under System logs and filterable by category.

  • Recorded: account creation, edits and password resets; tournament create, edit, activate and deactivate; database location changes; backups, filtered deletes and restores.
  • Not recorded: routine reads, and no password value ever — a reset records that it happened, never what it was set to.
  • Each entry carries the acting UID, the action, a detail object and a timestamp.

15Interface behaviour

Layout

Every dashboard is a stat row plus a section rail. At 900px and wider the rail is vertical and sticky beside the content so the whole set of sections stays visible; below that it folds into a horizontal scroller. A tab's content renders only while it is active, which is why the spreadsheet importer's 428 kB chunk is not fetched until Bulk upload is opened. Tabs whose module is off are dropped entirely.

Language

English and Tamil, switched under the settings gear. Interface text is translated; data is not — translating a competitor's name would be wrong and translating an event name would break the code that matches on it. A key with no Tamil string falls back to readable English rather than showing the key.

Day and night

Every colour is a token declared for day, for the OS dark preference, and for an explicit in-app choice, so the toggle wins in either direction and nothing below the token block hard-codes a colour. All 30 text-on-background pairs clear WCAG AA at 4.5:1. Chart palettes are validated per surface (adjacent colour-vision-deficiency ΔE 24.7 day, 26.8 night). The bout grid uses a single-hue sequential ramp rather than green/amber/red, because red and green sit ΔE 4.1 apart under deuteranopia — the two states most worth telling apart would have been the hardest.

Error surfacing

Field errors render under their field. A failed configuration fetch is reported as offline rather than as an app with every feature switched off, because modules arriving empty would otherwise read as a deliberately stripped interface.

Response conventions

  • 400 with { errors: { field: message } } for validation.
  • 401 unauthenticated, 403 wrong role, 404 missing record or disabled module.
  • 409 for a conflict that the operator can resolve — a bout already held, a destination folder that already holds data, a switch that would leave no Super Admin — carrying a code the interface uses to raise the right prompt.
